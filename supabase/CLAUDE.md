# supabase — Schema Postgres e políticas RLS

SQL aplicado manualmente no SQL Editor do painel Supabase — não há ferramenta de migration nem execução automatizada. Cada `.sql` aqui é a fonte de verdade para uma parte do schema/segurança e deve ser executável mais de uma vez sem erro.

## Responsibility

Definição de tabelas, funções `SECURITY DEFINER` e políticas RLS (Row Level Security) do banco. Não contém lógica de aplicação — quem chama essas tabelas/funções é `netlify/functions/_auth.js` (via `SUPABASE_SERVICE_ROLE_KEY`) e `scripts/supabase_dados.js` do lado do servidor, e o client anon direto em `painel.html` do lado do browser. Alterar uma policy aqui sem entender quem lê com qual chave (anon vs. service_role) é o tipo de erro que este diretório existe para prevenir.

## Key patterns

- Todo arquivo abre com um comentário-cabeçalho dizendo que é seguro rodar mais de uma vez ("idempotente") e onde rodar (SQL Editor do Supabase) — ver `rls_e_limite_de_uso.sql:1-5`.
- `create table if not exists` / `create or replace function` / `drop policy if exists` antes de `create policy` — nunca um `create table`/`create policy` puro que quebra numa segunda execução.
- Toda tabela nova tem `alter table ... enable row level security` logo após o `create table`, seguido de pelo menos uma `create policy` explícita — nunca deixe uma tabela sem RLS habilitado.
- Função que precisa escrever ignorando RLS usa `security definer` + `set search_path = public`, e em seguida `revoke all ... from public` / `grant execute ... to service_role` — para que só o backend (chave de serviço) consiga chamá-la, nunca o client anon do browser.
- Policy de leitura própria segue o padrão `using (auth.uid() = usuario_id)` — não widen isso para "qualquer autenticado" sem que seja uma decisão deliberada (ver a nota equivalente no `CLAUDE.md` raiz sobre RLS).

## Local conventions

- Nome de policy descreve tabela + ação + escopo (`"uso_diario_select_proprio"`) — mantenha esse padrão `<tabela>_<acao>_<escopo>` em policies novas.
- Ao mudar um `.sql` existente, edite o arquivo idempotente correspondente (não crie um `migration_NNN.sql` novo) e avise o usuário para re-rodar aquele arquivo específico no SQL Editor.
